PlanetaryStack

Module Planetary. Process > Planetary > PlanetaryStack. This document is installed with the module (doc/tools/PlanetaryStack/).

PlanetaryStack turns a planetary or lunar video into one image (lucky imaging). It reads the same videos as SERViewer: SER files, and uncompressed 8-bit greyscale or raw Bayer AVI files such as ASIAIR captures. It measures every frame, chooses the sharpest frames from the capture's own statistics, aligns them to the target and then region by region, and stacks them with outlier rejection. There is nothing to set: no percentage of frames to keep and no alignment points to place. When a capture has nothing usable, it makes no image and says why, with the numbers behind the verdict. From the stack it can also make a finished image: a mineral moon for the Moon, or a processed planet (colour-calibrated, dispersion-corrected and sharpened) for Mercury to Neptune, each tuned live with three sliders.

The interface

  • Open... chooses a .ser or .avi file with the same dialog and filters as SERViewer (“Open planetary video”). The info block shows the file name, frame count, size, bit depth and colour layout (for an AVI, the Bayer pattern and where it came from), plus any warnings from the reader. Opening a new file sets the Bayer pattern back to Auto. The file is read for this and closed again at once.
  • Bayer pattern (AVI only): Auto, None (mono), RGGB, GRBG, GBRG or BGGR, exactly as in SERViewer (see its documentation, “Bayer pattern and the ASIAIR sidecar”). This is the bayerPattern parameter.
  • Save pattern... (shown only for an AVI with no sidecar) remembers the pattern chosen above in a sidecar next to the video, as SERViewer's button does. It is enabled once you have chosen RGGB, GRBG, GBRG or BGGR and the stack made with it is shown: the stack's colours are how you tell the pattern is right. It asks first (“Write <name>.avi.txt with Bayer = RGGB? Auto will use it for this video from now on (SERViewer and PlanetaryStack).”) and never replaces an existing sidecar. See SERViewer's “Remembering a chosen pattern” for the file it writes.
  • Stack! stacks the video. The progress bar shows the step and how far it has got: “Step 1 of 3: Measuring frames” (with a frame count), “Step 2 of 3: Aligning” (a percentage), “Step 3 of 3: Stacking” (the frames stacked so far). The window stays usable while it runs.
  • Cancel stops a running stack. Nothing is left behind: no image and no file. A mineral moon or planet processing cancelled while it is made from a stack already shown (Mineral moon or Planet processing checked after Stack!) leaves that stack shown. Closing the window, or quitting PixInsight, cancels a running stack the same way and waits for it to stop.
  • The preview shows the stack, stretched for display only: black at the 0.5th percentile of its samples (the sky's level around a planet) and white at the 99.99th percentile, so one hot pixel or satellite trail cannot dim it. The image Execute opens is not stretched. Fit, 100%, 200%, − and + set the zoom; drag to move around a zoomed stack.
  • The info block shows the result: “Stacked: n of N frames used” and the time taken, every warning, then how the frames were chosen (Frames:) and how they were aligned (Alignment:). When no image can be made, the preview stays empty and the info block shows “No image:” with the diagnosis and the numbers behind it (see When no image is made).
  • Target: Auto, Other, Moon, Mercury, Venus, Mars, Jupiter, Saturn, Uranus or Neptune. Auto reads it from the ASIAIR file name (<date>-<time>-<Target>-Bin1 <Filter> <temp>F.avi); the combo shows where it came from, for example “Moon (from file name)”. Choose a target to override it. It is written to the image's OBJECT keyword, and it decides the processing offered beside it: Mineral moon and its sliders for the Moon, Planet processing and its sliders for any other target. Only that set is shown. Changing the target never stacks again.
  • Mineral moon (see The mineral moon) is offered when the target is the Moon, the capture is colour and the file name's filter is not a narrowband or an IR-pass one (a filter not named, or not recognised, is allowed). Narrowband: HaO3, S2O3, Ha, OIII (O3), SII (S2), Hb, D1, D2, Duo, NBZ, ALP-T, L-eNhance, L-eXtreme, L-Ultimate, CH4 (Methane); IR-pass: IR followed by a cut-on of 600 to 1100 nm (IR642, IR-685, IR850nm), IRPass, and ProPlanet or PP followed by one (PP742). Case does not matter, nor, in the IR-pass names, “-” and “_”. Otherwise the box is disabled and its tooltip says why, for example “Mineral moon needs a broadband filter; HaO3 is narrowband, so its colours come from the filter.” Checked after Stack!, the preview shows the mineral moon; unchecked, the stack again. Neither restacks.
  • Strength, Chroma blur and Sharpen tune the mineral moon live: each change re-runs only the colour and sharpening steps on the stack already made (a fraction of a second), never the stack itself.
  • Planet processing (see Planet processing) is offered when the target is Mercury, Venus, Mars, Jupiter, Saturn, Uranus or Neptune, the capture is colour and the file name's filter is not a narrowband or an IR-pass one: the same colour and filter rules as the mineral moon's above. Otherwise the box is disabled and its tooltip says why:
    • Target Other: “Planet processing needs a planet target; pick the planet in the Target list.” (the colour calibration needs a known body).
    • A mono capture: “Planet processing needs a colour capture; this one is mono (set the Bayer pattern if it is a colour camera).”
    • A narrowband or IR-pass filter, for example “Planet processing needs a broadband filter; IR685 is IR-pass, so its colours come from the filter.”
    Checked after Stack!, the preview shows the processed planet; unchecked, the stack again. Neither restacks.
  • Saturation, Chroma blur and Sharpen tune the processed planet live, as the mineral moon's sliders do: each change re-runs only the sharpening and colour steps on the stack already made.
    • Saturation, 0 to 3, default 1: the planet's colour as a multiple of its natural colour (the catalogue colour the stack was calibrated to). 0 is grey, 1 the natural colour, 3 the most. Highlights never clip: where a channel would, the colour gives way and the hue holds.
    • Chroma blur, 0 to 6 px, default 1: how far the colour is smoothed (frames up to 2000 px wide; scaled for wider ones). 0 is none. More hides the colour's noise; less keeps a planet's small colour features (belts, spots), a few pixels across. The detail always comes from the sharp luminance.
    • Sharpen, 0 to 4, default 1.5: how much the luminance is sharpened. 0 is none. On a small disc the finest detail gains most; noise is held back at every amount, and the sky is left as it is.
  • Execute (and Apply Global, the round button) opens the stack shown as a new image window, without stacking again. With Mineral moon or Planet processing checked it opens two windows, the stack and the mineral moon or the processed planet. If nothing has been stacked yet for the file and pattern shown, it stacks first and then opens the result. The file is read again first: if it has been replaced by a different capture (another frame count, size, bit depth or colour layout), the old stack is dropped rather than opened.

Dragging the interface's instance triangle onto the workspace saves a process icon with the file, Bayer pattern, target, mineral moon and planet processing settings (the Moon's and the planet's are kept apart, so each icon keeps its own); executing that icon stacks the file.

The mineral moon

A mineral moon exaggerates the Moon's subtle true colour differences (titanium-rich maria blue, iron-rich ones orange-brown) into a finished image. PlanetaryStack makes it from the stack itself, with no other process, in seven steps, each reported in one HISTORY line beginning PlanetaryStack mineral::

  1. Lunar disk: the lit disc and the sky are told apart.
  2. Colour calibration: the lit disc is the white reference (saturated pixels left out), the sky the background.
  3. Background: a sky plane is removed from each channel.
  4. Display transfer: a linked stretch puts the disc's median at 0.35 and keeps headroom above its brightest sample.
  5. Channel alignment: red and blue are moved onto green when atmospheric dispersion shifted them by more than 0.1 px (and the shift is well measured); at the frame's edge the colour ratio is taken from the nearest pixels inside.
  6. Sharpen: the luminance is sharpened on wavelet scales by the Sharpen amount, each scale limited by the stack's own measured noise, so the sky and smooth areas are not roughened.
  7. Mineral colour: each pixel's colour difference from neutral, taken from a blurred colour layer, is multiplied by Strength and applied to the sharp luminance. The brightest highlands fade towards neutral so they are not blown out or turned cyan, and no sample is clipped.

A step that cannot run (for example, too little sky to calibrate against) says why in its line and leaves the image as it was. If no lunar disc can be told from the sky, the result line and the Process Console say so.

The mineral moon opens as a second window, <name>_mineral, beside the linear <name>_stack. It is stretched for display (non-linear), 32-bit floating point, and carries the stack's keywords plus the seven mineral lines.

Planet processing

Planet processing turns a planet's stack into a finished, display-ready image in its natural colour: no grey Mars, no white Saturn. PlanetaryStack makes it from the stack itself, with no other process, in seven steps, each reported in one HISTORY line beginning PlanetaryStack planet: and naming what it measured:

  1. Planet disc: the disc (Saturn's rings included) and the sky are told apart, also for a small planet in a large frame of sky. The line gives the disc's size in pixels and its equivalent radius.
  2. Colour calibration: red and blue are scaled about the sky so that the disc's mean colour equals the planet's own colour relative to sunlight (green is unchanged; saturated pixels are left out). That colour is the ratio of the planet's geometric albedos in the Johnson B, Johnson V and Cousins Rc bands, from Mallama, Krobusek & Pavlov 2017, “Comprehensive wide-band magnitudes and albedos for the planets”, Icarus 282, Table 7. The camera's B, G and R are taken as B, V and Rc, an approximation the line states along with the source, the target ratios and the disc's colour before and after.
    PlanetB/GR/G
    Mercury0.7391.113
    Venus0.9550.955
    Mars0.5181.471
    Jupiter0.8230.954
    Saturn0.6791.295
    Uranus1.1500.541
    Neptune1.2710.511
    Saturn's values are the paper's at ring inclination 0, so they are the globe's; with the rings open, the disc's mean includes ring light, and its colour is that much off. The step is skipped, and the line says why, when the disc has fewer than 30 unsaturated pixels or a channel has no positive level. With under 1% of the frame in sky it runs without a background reference, and the line says so.
  3. Background: a sky plane is removed from each channel.
  4. Display transfer: linear, with no midtones stretch, as planetary images are shown. The brightest sample the stack did not clip is put at 0.95, so a dim capture (Neptune) is not left dark.
  5. Channel alignment: red and blue are moved onto green to undo atmospheric dispersion. The shift of each is measured on the disc's limb (not its interior, whose belts and markings would read as a shift), and a channel is moved only when its shift exceeds 0.1 px and three times its uncertainty; on a disc the frame cuts, only when that uncertainty is also within 0.05 px. Dispersion puts red and blue on opposite sides of green along one line, so when one channel passes and the other does not, the other is tested again along the first one's line and, if it passes there, moved along that line only. A shift that cannot be measured reliably (too small a disc, too little of its limb in the frame, a colour that differs around the limb) is declined, not guessed: the line gives each channel's shift, its uncertainty and why it was or was not applied.
  6. Sharpen: the luminance is sharpened on wavelet scales by the Sharpen amount, tuned for small discs (the finest scale gains most), each scale limited by the stack's own measured noise. The sky is not sharpened.
  7. Saturation: the colour, taken from a blurred colour layer (Chroma blur), is applied to the sharp luminance at Saturation times the natural colour. There is no highlight fade (Jupiter's zones and Saturn's rings keep their colour), and no sample is clipped: where a channel would pass full scale, that pixel's colour gives way and its hue holds.

A step that cannot run says why in its line and leaves the image as it was. If no planet disc can be told from the sky (a very faint planet, a frame of sky), the later steps are skipped, the result is the stack clipped to [0, 1], and the result line and the Process Console say so.

The processed planet opens as a second window, <name>_planet, beside the linear <name>_stack. It is display-ready (scaled linearly, not stretched), 32-bit floating point, and carries the stack's keywords plus the seven planet lines.

How the frames are chosen

Everything below is decided from the capture itself. The video is read from start to end several times (once to measure, once to align, once to stack, plus short reads in between); it is never held in memory whole.

  1. Hot pixels. 64 frames spread evenly over the capture (every frame of a shorter one) are examined. A sensor site that stands out on its own in at least 80% of them is hot, and is replaced in every frame by the median of its same-colour neighbours before anything else looks at the frame.
  2. Noise. The camera's noise at each brightness level is measured from runs of consecutive frames, so that noise is never mistaken for detail when frames are compared.
  3. Measuring every frame. For each frame: is the target there, where is it and how large, how sharp is it, and how much of it is saturated.
  4. Dropping unusable frames. Frames without the target, stray detections (a box of the wrong size, such as a satellite streak), frames where a planet touches the frame edge (a cut limb is never stacked), frames where at least a quarter of the target is at full scale, and frames with no detail at all are not used. A target that fills the frame (the lunar surface) is recognised as such: its frames are not dropped for touching the edge.
  5. Suspiciously sharp frames. A few frames far sharper than the rest may be glitches (a torn frame, a satellite in the target) or genuinely lucky frames. They are held back and decided by alignment: those that align as well as the other frames are stacked, the rest are not.
  6. How many to keep. The sharpness measured in one frame is itself noisy, so the frames are ranked by their sharpness with that noise allowed for statistically. Then the count is chosen: each extra frame lowers the noise of the stack, but is a little less sharp than the ones before it. PlanetaryStack keeps the number of frames at which the expected detail of the stack is greatest. A steady night keeps many frames, a poor night few. The Frames: line says how many were selected, the quality bound they meet (“quality ≥ x of the best”) and how many were left out for each reason above.
  7. Focus and seeing (a disc, not a frame-filling surface). The sharpest frames' limb is measured against the size of the disc. A disc blurred far beyond what in-focus captures show is refused (Out of focus, or Seeing too poor when the blur changes from frame to frame); a disc blurred less, but more than in-focus captures show, is stacked with a focus warning.
  8. Aligning. The 16 sharpest kept frames (torn ones left out) are averaged into a reference. Every frame is aligned to it with sub-pixel accuracy. Frames that match the reference clearly less well than the rest (below 0.85 of the median match, and never below a match of 0.5), such as shaken frames, are left out, and so are torn frames -- ones whose top and bottom halves line up with the reference more than 3 pixels apart (6 on a colour camera, aligned at half resolution). One limit: the reference is built from the largest group of the sharpest frames that agree with each other. If most of them are torn the same way (shifted in the same direction by a similar amount, even through different rows), that torn group becomes the reference, and the intact frames are the ones left out as torn. This has not been seen in real captures. The Alignment: line gives the frames aligned, the median match and the cut.
  9. Regions. Seeing blurs and moves each part of the image differently, so the image is divided into regions, placed automatically wherever there is structure to align on: about a quarter of a planet's width across, or an eighth of the frame's shorter side on a frame-filling target. Each region ranks the aligned frames by its own sharpness, keeps its own best ones by the same rule as step 6, and is aligned with its own small shift. The regions are blended smoothly, with no seams. Over the sky, where there is no detail to gain, the stack is the plain mean of all the frames stacked.
  10. Stacking. Each frame is debayered with an edge-directed method (Hamilton-Adams), which gives less colour error at sharp edges such as the limb than SERViewer's bilinear debayer, shifted onto the reference once, matched in brightness to the others (so frames chosen by different regions agree in brightness) and added. Samples that differ from the reference by far more than the frames normally do (a satellite or aircraft trail, a bird, a cosmic ray) are rejected. The Alignment: line ends with the share of samples rejected and the hot pixels repaired.
    On a Bayer capture, the outer 4 pixels of every frame are not stacked: the debayer has less to work with at a frame's edge, and its colour there is less accurate. The image is then cropped. First go the rows and columns at its edges that no frame reached once those 4 pixels are left out; nothing is filled in or invented there. Then, on each side, up to 4 more rows or columns go while fewer than half of the frames stacked there reached them: on a capture held nearly still those lines would be made of a handful of frames and be visibly noisier than the rest. A capture held still therefore loses about 4 or 5 pixels on each side (up to 8 where a few frames strayed further); one that drifted also loses the edges no frame reached. A mono or RGB capture leaves no frame border out, so only drift crops it. When anything is cropped, the Alignment: line ends with a clause saying how many pixels went from each side and why, for example “cropped 8 px left, 4 px top, 7 px right, 4 px bottom: no frame reached them inside its stacked part, except 4 px top, 4 px bottom, which under half of the frames stacked there reached (each frame's outer 4 pixels are not stacked)”.
  11. Focus check of the stack. The sharpest kept frames are split into two half-stacks; the detail the two have in common is free of noise, and is compared with in-focus captures. This check only warns, never refuses.

When no image is made

A capture with nothing usable gives no image and no preview. The info block (or, for a script, the Process Console and the error message) gives one of these diagnoses, followed by the numbers behind it:

DiagnosisMessage (numbers vary)What to change
No target“No target: the frames hold only background (a target in n of N frames).” A frame-filling target seen too rarely: “Too few frames show the target: a frame-filling target is seen in only n of N frames (cloud or gaps?); at least 10% of the frames are needed.” Check the target was in the field and not clouded out.
Target leaves the frame“The target leaves the frame: it touches the frame edge in n of N frames with a target, so only m show it whole; keep it centred while capturing.” Keep the planet centred (guiding, a larger capture area).
Clipped“The target is saturated: n of N frames have at least 25% of the target at full scale (median p%); lower the gain or the exposure.” Lower the gain or the exposure.
Out of focus“Out of focus: only n of N frames show any detail at all (the rest measure quality 0).”, or “Out of focus: even the sharpest frames blur the limb by b px, p% of the target's radius (usable: under u px), and the blur is the same in every frame ... -- the optics, not the air.”, or “Too blurred: ... -- focus or seeing, ...” when the frames cannot tell the two apart. Refocus.
Seeing too poor“Seeing too poor: the blur changes from frame to frame ..., and even the sharpest frames blur the limb by b px, ...” Capture on a steadier night or with the target higher.
Frames do not line up“The frames do not line up: only n of N selected frames match the reference well enough to be aligned (median match m, needed c; when any are torn: t torn: part of the frame displaced by more than p px) -- the view shook or changed from frame to frame (wind, a knock, or not one steady target).” Shield the telescope from wind and knocks; capture one target per video.

Warnings with an image

  • Focus. “The stack may be out of focus: ...” with the limb blur measured and the range in-focus captures show. For a frame-filling target the wording is “may be out of focus (or the capture is sampled far finer than the detail it holds)”: on a lunar surface, defocus and heavy oversampling look the same.
  • No Bayer pattern known. A raw Bayer AVI with no known pattern (no sidecar, Auto) is stacked as a mono image of the colour mosaic, with a warning: the result cannot be debayered afterwards, because every frame was resampled onto the stack. For colour, choose the pattern under Bayer pattern and Stack! again; Save pattern... then remembers it.
  • Warnings from the reader (a damaged file the reader recovered from, a sidecar it could not read) are shown as well.

The image it opens

  • 32-bit floating point, linear (not stretched), at the capture's sampling (no resizing), cropped as described under Stacking above, so a few pixels smaller than the capture on a Bayer capture or a drifting one: RGB for a Bayer or colour capture, mono for a mono one (and for a raw Bayer AVI with no known pattern, see above). Samples are normalised like SERViewer's, so the camera's full range maps to [0,1].
  • Identifier: the file name with every character other than letters, digits and underscores replaced by an underscore (an underscore is put in front if it starts with a digit), followed by _stack, for example Jupiter_stack. PixInsight adds a suffix if that identifier is already in use.
  • FITS keywords:
    • OBJECT: the target (from the file name or the Target setting), left out when it is Other.
    • SRCVIDEO: the video's file name (shortened to fit its card, keeping the extension; the full name is in HISTORY).
    • NFRAMES: the frames in the video, every one measured. NCOMBINE: the frames stacked.
    • DATE-OBS and DATE-END (SER only): the UTC times of the first and last frame stacked when the file has a timestamp trailer; otherwise DATE-OBS is the header's UTC start time. An AVI never gets either: it carries no trustworthy clock.
    • INSTRUME (the SER header's camera, or the camera named in an AVI's ASIAIR sidecar), TELESCOP, OBSERVER: left out when empty.
    • No BAYERPAT: the stack is debayered RGB, or mono.
    • HISTORY: the PlanetaryStack version and the full file name, an AVI's Bayer pattern and its source, the frame selection and alignment lines, the frame counts with the time each step took and the data read, and every warning. Text longer than one FITS card continues on the next HISTORY card.
    Keyword text is plain ASCII: any other character is shown as ?.

The Process Console gets the same lines: the capture and the number of threads when the stack starts, then the warnings, the selection and alignment lines, and the frame counts with the time each step took and the read rate (MB/s). A slow run on a network drive can be put down to the read rate.

Memory and threads

PlanetaryStack uses every processor thread PixInsight allows. Each thread opens its own reader of the video. It plans its working memory to stay within 4 GB, using fewer threads where a large frame needs it; it holds about one frame per thread plus the stack being built, never the whole video. A frame too large for that budget still stacks, on one thread.

Files, network and external programs

  • Files read: only the video file you choose and, for an AVI, its sidecar <name>.avi.txt next to it (if present).
  • Files written: stacking writes no file. The only file PlanetaryStack writes is the sidecar <name>.avi.txt next to an AVI, and only when you click Save pattern... and answer Yes. It is written to a temporary <name>.avi.txt.partial file beside it first and then moved into place; the partial file is removed if the write fails, and a regular .partial file left there by an interrupted earlier write is deleted before writing (a symbolic link or anything else that is not a regular file at that path is left alone, and the write is refused). The stack opens as a new, unsaved image window; saving it is up to you.
  • Network: PlanetaryStack makes no network connection.
  • External programs: PlanetaryStack launches no external program.
  • It stores no settings or other files of its own, inside or outside the PixInsight installation.
