Refining Disambiguation — Minimal-Prompt Defaults

Your guidance simplifies the no-FILTER case. One residual case (unknown FILTER value) needs an explicit call.

Confirmed defaults from your input
No FILTER keyword in FITS + Bayer pattern detected (color OSC)
   ⤳ Treat as BROADBAND_OSC → OSC-as-LRGB pipeline. No prompt.
   ⤳ Auto-synthesise L from R+G+B for the LRGB combine path.

No FILTER keyword + mono (no Bayer)
   ⤳ Treat as generic mono — assigned temp filter name like "L_unnamed".
   ⤳ Single-channel stack + stretch + emit. No prompt.
Open question — FILTER keyword PRESENT but value unrecognised
Example: FILTER = "ALP-T 5nm" — Antlia's dual-NB filter, but our shipped
QE DB doesn't have it (or user mistypes the name "L-Quad" as "L_Quad" and the
fuzzy alias table doesn't catch it).

Two reasonable choices:
  - silent default by sensor type (loud Process Console warning) — matches your
    minimal-prompt direction, but if it WAS a dual-NB filter we silently
    fall back to plain OSC and recreate the green-M17 problem
  - loud failure at batch start — refuses to process, points the user at the
    override JSON; consistent with the "no silent fallbacks" rule

Pick what you want for this case:
A

Loud-fail at batch start, point at override JSON

Process Console: "FILTER='ALP-T 5nm' on 30 frames not in QE DB. Add it to ~/.nukex4/qe_overrides.json (see docs) and retry, or remove the FILTER keyword to default to plain OSC."

Pros: consistent with no-silent-fallbacks; can't accidentally re-create the green-M17 problem with a real dual-NB filter; user gets a precise instruction.

Cons: first-run pain if the user's filter isn't in our DB. They have to edit JSON to proceed.

B

Silent default by sensor + loud Process Console warning

Default Bayer→plain OSC, mono→generic L. Console: "WARNING: 30 frames have FILTER='ALP-T 5nm' which is not in QE DB. Treating as plain OSC. If this is a narrowband filter, add it to qe_overrides.json and re-run."

Pros: first-run never blocked; matches the minimal-prompt direction.

Cons: if it WAS a dual-NB filter the user forgot to register, we silently produce the bad output. Console warning is the only signal.

C

Tiered — loud-fail for OSC unknown filter, silent default for mono unknown

Mono unknown → temp name + proceed (mono filter mismatch is low-risk; you only get one channel either way).
OSC unknown → fail loud (because the dual-NB-vs-broadband distinction is the high-impact case).

Pros: matches minimal-prompt for the low-risk case while protecting the high-risk one.

Cons: two policies to remember; user might find the asymmetry surprising.
