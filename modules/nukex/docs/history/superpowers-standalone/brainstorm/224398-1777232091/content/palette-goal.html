Output Palette Goal

Before we design the channel pipeline, we need to fix the target. "No greens" is the constraint — but where exactly should HOO and SHO land on the color wheel?

A

True emission-line color (scientifically calibrated)

Each line maps to its actual visible-light color: Ha 656nm → red, OIII 501nm → teal/cyan, SII 672nm → deep red.

HOO result: Ha-bright regions go red, OIII-bright go cyan, mixed regions go magenta-violet (purple). No greens by construction.

SHO result: SII regions go deep red/maroon, Ha goes red-orange, OIII goes cyan. The palette has reds-through-cyan only — green is mathematically excluded.

Why pick: defensible, reproducible, matches what the photons are physically.

B

HOO traditional with SCNR-style green suppression

Ha→R, OIII→G+B (cyan), then explicitly subtract G from output to chrominance-limit. Standard PixInsight pattern: SCNR removes green chromatic noise after combine.

Result: traditional HOO look (R + cyan), green never present in output.

Why pick: matches what most users expect; comparable to existing PI workflows; easy to verify against reference processors.

C

Foraxx-style or custom palette mapping

Apply a non-linear remapping function (Foraxx, Bicolor, Adaptive HOO etc.) that distributes the line signals creatively across the output color wheel. Often used to push Ha into orange and OIII into deep blue, opening more visual contrast.

Result: visually striking but not literally calibrated — popular on AstroBin.

Why pick: processing flexibility / artistic latitude.

D

Both A and C — calibrated default + selectable preset

Ship A (calibrated emission-line color) as the default, also expose B / Foraxx as named presets the user can switch to per-stretch. Auto picks A unless overridden.

Why pick: sets a scientific baseline AND keeps creative flexibility. Stays with the v4 "Auto picks correctly out of the box" theme.

Cost: bigger UI surface; preset framework needs to be designed up-front.
