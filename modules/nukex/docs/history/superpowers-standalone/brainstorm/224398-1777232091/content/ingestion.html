Multi-Filter Ingestion

An SHO image needs HaO3 frames + S2O3 frames. An LRGB-mono image needs L + R + G + B sets. How does the user hand them to NukeX?

A

Single batch, auto-route by FITS FILTER keyword

UI stays as-is. User drops every frame from every filter into the existing file list. NukeX reads FILTER from each FITS header, groups frames by filter automatically, stacks each group, then combines.

Example FITS values seen in the wild: HaO3, S2O3, L, R, G, B, Ha, SII, OIII, L-eXtreme, ALP-T.

Pros: zero UI surface change. Honors "simple UI" rule. Works for all combos (HaO3-only, S2O3-only, HaO3+S2O3, LRGB-mono, plain OSC, plain mono).

Cons: garbage-in-garbage-out if FITS headers are wrong; needs a FILTER-name normalization table that handles aliases.

B

Per-filter file lists in the UI

Add tabs or expandable sections in NukeXInterface: "Lights (HaO3)", "Lights (S2O3)", "Lights (Ha)", "Lights (OIII)", etc. User drags frames into the right bucket.

Pros: explicit; impossible to misroute on bad FITS. Familiar to APP / WBPP users.

Cons: breaks the "simple UI" rule. The interface gets noisy. More code in NukeXInterface.

C

Multi-pass workflow (per-filter NukeX runs, then a combine tool)

User runs NukeX once for HaO3, once for S2O3, gets two intermediate FITS images. A separate "Combine" mode (or a follow-up Process) combines them.

Pros: separation of concerns; easy to swap a single filter's stack without redoing everything.

Cons: two-step workflow conflicts with NukeX's "one-shot finished image" promise. Combine state has to live in saved FITS metadata or a sidecar file.

D

A primary, with a fallback if FILTER is missing

Default to A (auto-route from FILTER). If the keyword is missing or unrecognized, surface a small disambiguation dialog asking the user to confirm the filter for that frame batch — once, with a remembered choice.

Pros: zero-friction common case + graceful handling of bad/exotic data. Honors the "simple UI" rule.

Cons: small UI escape hatch to design and test.
