Where in the pipeline does channel decomposition happen?

Three architecturally-distinct approaches. Each has SNR, code-modularity, and voxel-structure consequences.

Pipeline today (simplified)
FITS frame → Debayer → Align → Cache → Cube accumulate → Phase B fit/select → Stretch → Emit
Each frame is independent until "Cube accumulate". Voxel holds per-pixel statistics across all frames.

Three approaches — pick one

A

Decompose at debayer time (filter-aware DebayerEngine)

FITS → DebayerEngine[filter-class-aware] → emits {Ha, OIII} or {R,G,B} or {SII,OIII} per frame → Align → Cube

The DebayerEngine reads filter class + camera, applies QE matrix solve per pixel, emits already-decomposed channels. Stacker downstream sees clean line-emission channels for NB-OSC; clean R/G/B for plain OSC.

Voxel for HaO3: stores Ha + OIII + per-line stats. No raw R/G/B kept (lost after debayer).

Pros: downstream stages (align, stack, stretch) don't care about filter class — they just see "channels"; clean separation; voxel remains canonical truth.

Cons: per-frame decomposition has lower SNR than post-stack decomposition (each Q-matrix solve uses one frame's data); changing QE coefficients later requires re-running debayer; filter-class coupling lives in DebayerEngine.

B

Decompose at cube-finalization (after Phase B fit/select)

FITS → Debayer[naive RGB] → Align → Cube → Phase B fit/select on R,G,B → ChannelDecomposer{filter-class} → {Ha,OIII} → Stretch

DebayerEngine stays naive — emits R/G/B always. Stacker accumulates R/G/B voxels. After Phase B selects best pixels, a new ChannelDecomposer pass applies the QE matrix to the stacked R/G/B values, emitting line-emission channels.

Voxel: raw R/G/B stays canonical through Phase B. Line-emission channels appear at finalization time as a derived projection.

Pros: highest-SNR decomposition (operates on stacked-and-fit pixels, not single-frame); QE coefficients can change without re-running stack; existing Phase B logic is filter-class-agnostic.

Cons: two channel "shapes" exist in the codebase (raw R/G/B before Phase B; line-emission after); voxel structure has to accommodate both (or hold raw and add derived); one extra pass over the cube.

C

Per-frame decompose into voxel from day one (filter-aware accumulate)

FITS → Debayer[naive RGB] → Align → Cube[per-line voxel slots] → accumulate(R,G,B) into Ha/OIII slots via QE solve → Phase B fit/select on Ha,OIII → Stretch

DebayerEngine stays naive. Voxel grows to hold per-emission-line slots (Ha welford+histogram, OIII welford+histogram, SII welford+histogram, plus L/R/G/B for broadband). At cube accumulate time, the QE matrix routes incoming R/G/B values into the correct line-emission slots.

Voxel: from the first accumulated frame, holds whatever the filter class implies (Ha+OIII for HaO3; SII+OIII for S2O3; R+G+B for plain OSC; L+R+G+B for LRGB-mono).

Pros: Phase B fit/select operates on the line-emission channels directly (matches the user's "voxel is canonical record" rule cleanly); per-line per-frame data accumulated with full statistics; supports the LRGBSHO multi-class case (each frame routes to the correct slots based on its FILTER keyword).

Cons: voxel structure is more complex (variable slot count by filter class); accumulate step has a per-filter dispatch; Phase B fitting code has to accept that "channels" can be Ha/OIII not R/G/B.

Common ground: all three approaches use the same filter taxonomy, the same QE database, the same Lab/LCH composer at output time, and produce the same final RGB image for a given input. They differ in when the QE solve happens and what the voxel holds across the pipeline.
