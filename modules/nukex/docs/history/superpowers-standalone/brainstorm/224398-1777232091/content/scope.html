Color Science Overhaul — Scope

You raised two related-but-distinct issues. Which scope feels right for one design doc?

A

Bundled — full color-science overhaul

Includes: OSC-as-LRGB synthesis (Q1) + Bayer-NB decomposition with QE-aware OIII recombination (Q2) + palette/no-greens output, all in one design.

Why pick: the two share infrastructure — channel_config refactor, output composer, color-space helpers. One design, one plan, one regression sweep.

Cost: bigger spec, longer implementation phase, single big commit point.

B

Narrowband first (Q2 only)

Includes: Bayer-NB decomposition + QE-aware OIII recombination + no-greens palette. OSC-as-LRGB is a separate later design.

Why pick: M17 bothered you today; this fixes the visible bug fastest. OSC-as-LRGB is a quality lift you can stage independently after this lands and is field-tested.

Cost: two smaller designs over time. Some duplicated channel-config thinking.

C

OSC-as-LRGB first (Q1 only)

Includes: luminance synthesis + Lab/LCH composite for OSC and MONO_LRGB. Narrowband fix waits.

Why pick: broader user impact (every OSC user benefits), simpler to design, lower regression risk.

Cost: M17 stays green until next cycle.

D

Reframe — they're different beasts, do them in parallel

Includes: two parallel design docs and plans. Each ships independently. Explicit shared-infra contract between them.

Why pick: if the user thinks the two problems pull in opposite architectural directions and shouldn't be coupled.

Cost: overhead of coordinating two streams; risk of incompatible refactors.
