v4.0.1.0 has 6 E2E pixel-hash baselines (NGC7635 stacked / noise / stretched, plus GHS / MTF / ArcSinh sweep). Touching the channel pipeline changes some outputs by design. Need a policy.

A

Strict — every existing baseline stays bit-identical

The MONO_LRGB and OSC_RGB output paths must produce byte-for-byte identical results to v4.0.1.0. New paths (Bayer-NB, LRGBSHO) get fresh baselines.

Cost: requires gating new behavior behind an opt-in flag for existing users; defeats some of the L-synthesis benefit (existing OSC users don't get it unless they ask).

Why pick: zero-risk for the user who upgrades and expects nothing to change.

B

Pragmatic — single-channel stretches stay bit-identical, multi-channel paths re-baseline

Sweep tests (GHS / MTF / ArcSinh single-channel) must not move — they verify stretch math, which we don't touch. The LRGB-mono multi-channel and OSC paths get new baselines because the channel pipeline genuinely changed.

Cost: need to verify "before vs after" looks right on real data (M27 bench, NGC7635) and document why the change is correct.

Why pick: matches what the design is actually doing — the math we trust stays trusted, the paths we're rewriting get re-validated. No opt-in flag drift.

c

Wholesale re-baseline

Treat this as a v5.0.0 release. Every E2E baseline is replaced; cold-flake tracking starts fresh. Document each rebaseline.

Why pick: simplest mental model. Gives implicit cover to any incidental drift in numerical paths we touched obliquely.

Cost: loses the regression floor of stretch correctness — might mask a real bug introduced by the refactor that happens to also produce a "reasonable" image.

Note on versioning: regardless of policy choice, the API surface that callers depend on (PCL Process parameters, FITS keyword writes) needs explicit migration. Picking "B" doesn't free us from documenting "OSC output now has 4 channels; here's how downstream PI scripts adapt".
